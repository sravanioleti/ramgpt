# RamGPT - Ticket Resolution Intelligence

RamGPT is a working pilot for the `RamGPT_Ticket_Resolution_assignment`. It
helps a service-desk operator resolve a new ServiceNow ticket faster without
pretending to replace ServiceNow or human accountability.

> **Submission summary:** This repository contains a working prototype, a
> complete architecture/design document, a runnable one-command launcher, and
> an explainable human-approval workflow. See
> [ARCHITECTURE.md](./ARCHITECTURE.md) for the HLD, LLD, API design, schema,
> sequence diagrams, controls, and evaluation plan.

## Prioritized capabilities

1. **Similar historical ticket retrieval** - hybrid BM25 keyword retrieval, TF-IDF baseline, and `all-MiniLM-L6-v2` semantic embeddings indexed with FAISS return the top five precedents and their proven resolutions.
2. **Confidence-based decision engine** - uses a deterministic, explainable score: `50% retrieval similarity + 30% historical assignment-group agreement + 20% evidence quality`. Bands are `High >= 80%`, `Medium >= 60%`, and `Low < 60%`. Similarity is never presented as correctness.
3. **Human-in-the-loop approval** - proposed routing/resolution is persisted as pending and cannot become approved or rejected until a named reviewer acts.
4. **Human feedback / learning loop** - thumbs-up/down, corrections, and reviewer decisions are stored in SQLite for evaluation and future model improvement.
5. **Conversational case workspace** - each ticket has a persisted chat transcript, with context extraction and re-analysis as the conversation adds facts. The current UI keeps one active case per session; the API supports reopening a case by ticket ID.

The extra guardrail is an explicit state machine: RamGPT only prepares a handoff payload; a future ServiceNow adapter would be the only component allowed to apply it after approval.

## Architecture

The system has a Streamlit conversational workspace, a FastAPI orchestration
API, SQLite audit storage, hybrid BM25/TF-IDF/FAISS retrieval, optional Gemini
grounded generation, an explainable confidence policy, and a human approval
boundary before any future ServiceNow write. The full architecture diagram and
low-level design are in [ARCHITECTURE.md](./ARCHITECTURE.md).

## Ticket walkthrough

1. Operator enters a short description and context in the chatbot workspace.
2. The API retrieves the closest resolved tickets and shows the evidence, assignment group, and resolution.
3. The decision engine computes a bounded confidence score. Weak matches are explicitly marked for human review.
4. A proposed ticket is stored as `pending_approval`; no external state changes happen.
5. A reviewer approves or rejects the recommendation. The API records who acted and why.
6. The operator rates the outcome or supplies a correction. Feedback is stored alongside the ticket for offline evaluation/retraining.

For low-confidence tickets, RamGPT does not show a specific historical resolution as if it were a diagnosis. It shows missing information, questions for the requester, generic investigation steps, and a structured handoff summary instead.

The chat supports follow-ups such as “Why is confidence low?”, “Show me the most similar ticket”, and natural evidence updates such as “I am getting error 691 and only one employee is affected.” Those updates change the case context and trigger a fresh analysis. Clearing the UI or starting a new conversation does not delete the underlying ticket record.

## Run locally

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# Start both the API and frontend together
python run.py
```

Open `http://localhost:8501`. The API health endpoint is `http://localhost:8000/api/health`.

The launcher starts the FastAPI backend automatically, opens the Streamlit frontend,
and stops the backend when the frontend exits. You only need one terminal.

## AI configuration

The retriever uses `all-MiniLM-L6-v2` sentence embeddings in FAISS, BM25 keyword
retrieval, and a TF-IDF baseline blended into one ranked evidence list. If
`GEMINI_API_KEY` (or `GOOGLE_API_KEY`) is set, chat responses are generated by
Gemini using the conversation and retrieved tickets as grounding context. Without
a key, the same retrieval and confidence engine runs with a deterministic
conversation fallback; it never fabricates a resolution.

Application startup downloads the small Hugging Face model once and builds a
cached FAISS index at `.cache/historical_tickets.faiss`. This is embedding
inference, not model training. The one-command
launcher waits for that startup work to finish before opening Streamlit, so the
first ticket request does not time out. For a deliberately offline smoke test,
set `RAMGPT_DISABLE_SEMANTIC=1`; normal runs should leave it unset.

The first build must finish once. After that, subsequent `python run.py`
launches load the cached index and do not encode the historical dataset again.
Do not stop the first build before it completes, or it will need to resume from
the beginning on the next launch.

```powershell
$env:GEMINI_API_KEY = "your-key"
python run.py
```

### Using Gemini through `.env`

Do not paste the API key into Python files. Create a local `.env` file:

```powershell
Copy-Item .env.example .env
notepad .env
```

Set:

```text
GEMINI_API_KEY=your-real-gemini-api-key
GEMINI_MODEL=gemini-1.5-flash
```

The backend loads `.env` automatically. `.env` is included in `.gitignore` and
must never be committed. The first assistant response and every follow-up chat
message call Gemini with the current conversation, case context, confidence
analysis, and retrieved historical evidence. If Gemini is unavailable, the
grounded deterministic fallback is used and the API logs the reason.

## API surface

* `GET /api/health` - report API readiness, retrieval mode, and Gemini availability
* `POST /api/tickets/analyze` - retrieve evidence and create a pending recommendation
* `GET /api/tickets` - inspect recent pilot tickets
* `GET /api/tickets/{id}` - reopen a ticket and its persisted conversation
* `GET /api/tickets/{id}/analysis` - recalculate analysis without creating a duplicate case
* `POST /api/tickets/{id}/chat` - append a user message, generate an answer, and re-analyze
* `POST /api/tickets/{id}/decision` - approve, reject, or edit with reviewer identity
* `POST /api/tickets/{id}/feedback` - capture rating and corrections
* `GET /api/evaluation` - run a reproducible nearest-neighbor team-retrieval proxy and show human-feedback counts

## Why this stack and what I would build next

Python keeps the retrieval and evaluation path close to the API and makes the prototype easy to run. FastAPI gives typed, inspectable contracts; Streamlit makes the operator workflow visible quickly; SQLite makes the approval and learning audit trail durable without production infrastructure.

For production I would add authentication/RBAC, a proper relational database, embedding retrieval with a domain-tuned model, model/version and threshold registries, PII redaction, ServiceNow webhooks with idempotency, a human-labeled resolution benchmark, offline replay evaluation, and monitoring for drift, abstention rate, reviewer overrides, and time-to-resolution. The pilot intentionally does not rebuild ServiceNow, manage assets, or claim autonomous closure.
